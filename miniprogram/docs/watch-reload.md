# 增量构建后的页面注册提示与交互失效

日期：2026-10-19。现象：修改代码后，开发者工具提示“页面 [pages/dev/components/index] 未配置在 app.json 中”，页面随后无法操作。

## 已确认的原因与边界

- **同步时序（跨层契约）**：原同步 writeBundle 未设等待约束，会与其他异步输出钩子并行。真实 Vite 回归复现了最终处理尚未结束，目标已经收到初始版本的情况。
- **无变化文件通知（隐含假设）**：rsync 的 archive 模式包含时间保留。Taro 重建后即使 app.json 字节相同，目标时间仍被更新；开发者工具日志确实记录了 app.json 和页面配置的变更事件。校验和一致不等于没有文件事件。
- **本地热重载覆盖**：共享 project.config.json 关闭了 compileHotReLoad，但当前 Windows 目标的 project.private.config.json 将其开启，本地设置优先。

排查时源／目标 app.json 均包含全部九个路由，没有观察到文件缺页或被截断。上述同步缺陷及配置冲突已确认；它们与开发者工具内部页面注册状态的具体因果关系，仍需运行时反馈验证，不能将文件检查通过当成点击恢复。

## 修复

- Windows 同步采用 post/sequential 的 writeBundle 钩子，等待前面的异步输出处理完成。
- 保留校验和镜像与删除规则，通过 --no-times 避免将源文件的纯时间变化传播到目标；真正的内容变化仍正常发布。
- 当前 Windows 工程的私有 compileHotReLoad 已关闭，其他字段保留并在本机临时目录备份；同步器继续保留私有配置，不在每次构建时强行覆盖用户设置。
- 已重启 watch 加载新插件。用户确认普通编译后仍无法点击，因此不能把关闭热重载与普通编译视为运行时恢复保证。

## 运行时验证

开发者工具版本为 2.02.2610162 Nightly，基础库 3.17.4。通过当前版本的本机调试接口重新初始化小程序运行环境后，调试通道的 Navigator 点击与 navigateTo 均成功；随后用户确认鼠标点击分类入口恢复正常。恢复前后没有修改页面事件、组件样式或路由配置。

此结果说明卡住状态可以通过重新初始化运行环境恢复，但尚不能断言同步缺陷就是交互失效的唯一根因。调试通道的点击成功与用户鼠标点击恢复分别记录，不能互相替代。

恢复后再次触发组件索引页增量构建：运行时九个路由齐全，206 个产物同步一致，app.json、project.config.json、base.wxml 的内容和修改时间保持不变。用户确认鼠标从首页进入组件索引、再进入分类页均正常，运行时页面栈也显示首页 → 组件示例 → 导航组件。

用户补充：故障并不稳定复现，开发者工具长时间打开后有时突然无法点击，已遇到多次。因此本次记录为“当前恢复、一次增量回归通过”，不能记录为偶发卡死已根治。同步时序与时间戳修复作为已验证的构建改进保留；后续若再次发生，需同时留取工具版本、运行时状态和是否仍能通过调试通道操作的证据。当前使用 Nightly，日常开发可使用稳定版对照观察，不能未经对照就认定具体版本缺陷。

当前版本的本机 CLI HTTP v2 接口使用 project 参数；旧客户端发送的 projectpath 会返回缺少 project / appid，不能据此判定工程没有打开。调试接口仅用于本次定位，未加入工程依赖或日常构建流程。

此前检查偏重于构建结束后的文件内容、模块导出和模板编译，没有覆盖发布时序、纯时间变更事件及本地配置优先级。这是回归覆盖缺口，新增验证分别覆盖这些边界。

## 后续排查约定

### 同日复发记录

列表 Cell 间距调整后的增量构建完成后，用户再次报告组件索引页和设计规范页“未配置在 app.json 中”，并确认两个入口均无法通过鼠标打开。本次复查：源／目标 app.json 均注册全部九个页面，各页面的 JS、JSON、WXML 齐全；206 个产物逐字一致，共享与私有 compileHotReLoad 均为 false，只有一个正式 Taro watch。目标 app.json、project.config.json、base.wxml 的修改时间仍与上次成功增量验收记录一致。

这次复发说明已有同步改进和关闭热重载不足以保证开发者工具持续可交互，不能再将它们描述为该故障的完整修复。工具日志中存在重复模拟器上下文注册及 markDevLaunchEnv timingData not found，但这些内部日志与页面提示之间的因果关系尚未证实；读取模拟器 Console 的接口因本地工具授权超时未取得结果。本次未改业务路由或点击事件，先保存现场日志和配置，再尝试重置当前项目文件索引、关闭并重新打开项目窗口；恢复与否需以用户鼠标反馈为准。

用户随后反馈 CLI 操作没有正常完成重启，手动重启开发者工具后两个入口恢复。本轮恢复应归因于用户手动重启后的观察，不能使用 CLI 返回成功替代实际恢复证据；具体根因仍未确认。

用户同意重试并授权后，以 clientName=codex 连续读取 Console 成功。先筛选“未配置、app.json、TypeError、SyntaxError、Error、error、warn”未命中，再以 `grep -n .` 获取全量缓冲区；只返回基础库 3.17.4、React DevTools 和 Apollo DevTools 的启动信息。本轮重启前 Console 未能取得，重启后的正常日志不能证明旧提示的根因。后续同类故障优先由代理在已授权的工具入口拉取 Console，保存现场后再执行恢复操作，避免要求用户重复复制日志。

通过 Windows CLI 操作已导入工程时使用 Windows 标准绝对路径（反斜杠）。当前版本将同一目录的正斜杠形式识别为未导入的临时项目，不能将这种新窗口的状态当作原窗口恢复的证据。

遇到同类问题，分别检查路由文件、构建发布时序和开发者工具运行时。先确认正在导入的工程目录、私有热重载设置和唯一 watch，再检查模块与模板。不要仅通过补路由、重启工具或比较最终文件来判定根因。真实导航与触摸恢复单独记录。

相关规则已同步到小程序 spec 的“同步与发布”和 README 的 Windows 同步说明。
