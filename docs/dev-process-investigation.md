## 1. 原始调查结论与证据等级

本轮确认两项开发运行链路缺陷：**验收与日常开发共用构建目录**、**监管器仅监视 Air 进程存活**。隔离实验分别复现了跨实例删除二进制路径，以及新程序监听失败后继续由旧程序响应的现象。另有 8080 内嵌 SPA 与 5173 Vite 源码入口的更新方式差异。

旧业务进程最初脱离 Air 管理的精确时序仍待锁定。Air 并发重建与代际句柄切换存在待验证的竞争窗口；本轮正常保存、连续保存和集中释放构建的对照均恢复到最终版本，长期残留尚未在这些对照中复现。共享输出目录实验能证明互相干扰，长期进程泄漏的归因需要额外证据。

- Air v1.64.5 的 `runner/engine.go:696-708` 在停止旧程序且启用 `stop_on_error` 时删除配置中的二进制路径；删除依据是共享路径。

隔离实验使用同一构建输出、两个随机端口，分别启动 A 和 B。停止 B 后观测：

| 检查                   | 结果             |
| ---------------------- | ---------------- |
| A、B 端口              | 分别独立         |
| 停止 B 前二进制存在    | 是               |
| 停止 B 后二进制存在    | 否               |
| A 的 Air 进程          | 仍存活           |
| A 的 HTTP 服务         | 仍响应           |
| A 的 `/proc/<pid>/exe` | 显示 `(deleted)` |

因此，端口及数据库隔离之外，还需要源码、构建目录和清理权限隔离。`(deleted)` 本身证明磁盘路径与运行程序脱节，版本判断还需结合响应和构建标识。

## 4. 已确认：监管器可维持失效的开发会话

`scripts/dev.py:115-122` 对 Vite 包装器和两个 Air 进程执行 `poll()`。它缺少以下运行期核验：业务子进程退出码、实际监听 PID、预期构建版本、Web／Worker 代际唯一性。

隔离实验先启动本轮拥有的旧 HTTP 程序，再让 Air 启动新程序监听同一随机端口：

- 新程序打印 `address already in use` 后退出。
- Air 继续运行，`poll()` 返回 `None`。
- HTTP 响应始终来自旧 PID `896302`，版本为 `old`，预期版本为 `new`。

这复现了问题的持续机制：一旦旧进程占住端口，新程序启动失败，外层监管循环仍将 Air 视为存活，页面继续访问旧实现。当前启动前的端口检查可阻止第二次占用相同端口的 `pnpm dev`；运行期重建还需要同等级别的检查。

## 5. 待验证：Air 重建代际切换竞态

核验本地工具为 Air v1.64.5，编译工具链为 Go 1.26.8。锁定版本源码位于 `.tools/gopath/pkg/mod/github.com/air-verse/air@v1.64.5/runner/`。

静态风险：

1. `engine.go:421-433` 使用共享 `buildRunCh` 取消构建；`engine.go:503-511` 的完成阶段从同一共享 channel 取值。连续变更可能使旧构建的完成逻辑消费后续构建的 token，影响后续取消与串行化。
2. `engine.go:749-752` 的旧进程停止与新 `binStopCh` 登记分为两个步骤；并发 `runBin` 的切换需要核验原子性。
3. `engine.go:669-679` 的进程退出分支直接清空全局 `binStopCh`，缺少对该句柄是否仍属于当前进程代际的比较。
4. `engine.go:797-803` 中停止确认的等待上限为 5 秒；项目的 `kill_delay` 配置为 6 秒。重建、清理和应用优雅退出期限需要统一核对。

这些属于源码审查发现的风险点，具体触发历史现场的路径仍待实验确认。当前对照：

| 150ms 启动延迟，6 次间隔保存              | 每次返回预期版本               |
| 0.8 秒额外构建延迟，24 次连续保存         | 最终恢复 r24，静置后仅一代应用 |
| 150ms 启动延迟与连续保存，24 次           | 最终恢复 r24，静置后仅一代应用 |
| 阻塞 12 次构建后集中释放，再追加 3 次保存 | 最终恢复 r15，静置后仅一代应用 |

既有验收主要覆盖少数顺序重建、接口版本变化及整体退出。Worker 检查使用累计“就绪”日志数量，需要补充每代旧 PID 消失、实例数量和故障后的版本核验。

## 6. 前端入口的更新方式

- 5173：Vite；`DASHBOARD_SOURCE=1` 映射公共 Dashboard 源码，使用 HMR。
- 8080：Go 的 `webui/embed.go:11-16` 内嵌 `dist` 快照。

## 7. 建议修复顺序与验收门槛

1. **运行隔离**：每次开发／验收使用独立运行目录、Air 配置、Web／Worker 输出和清理范围；验收使用包含本轮工作区改动的独立源码快照，避免向日常 checkout 写入临时验收标记。公共前端产物同样隔离。
2. **代际监管**：重建串行执行；确认旧进程组完全退出及端口释放后启动新一代；核对实际监听 PID 与构建指纹。新一代失败时给出明确失败状态，清晰暴露旧进程占用情况。
3. **回归补齐**：覆盖长时间连续保存、编译失败后恢复、新程序监听失败、优雅退出超时、两组不同端口的实例并行、单组退出保留另一组产物，以及每代 Worker 单实例断言。Air 版本调整或替代监管方案均以这些回归结果作为选择依据。
